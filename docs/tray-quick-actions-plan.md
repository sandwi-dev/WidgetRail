# Tray quick actions

## Outcome

From the radial chooser, a single physical D-pad press runs a favorite independently of the selected widget. New profiles start with all four directions empty. Pressing an empty direction opens the widget action chooser. Assignments are shared by the rail and wheel and scoped to the profile.

## Interaction and appearance

- The left stick selects wheel sectors, A opens the selected widget, the center retains right-stick paging and the page number. Keyboard arrows continue to navigate the wheel. Physical D-pad taps run favorites or open assignment for an empty direction. No hold shortcuts in the first version.
- Place each assigned hint just outside the matching sector, e.g. Up above the power icon. Keep labels upright and tied to screen direction through changes of wheel page, highlighted widget, and overlay position. Fit long, translated labels, compact viewports, large text and screen edges. Keep the center clear. No four permanent empty buttons. An empty direction immediately opens assignment for that slot; unavailable assignments remain visible with a reason and never open the editor implicitly.
- Mouse and keyboard users open a native Quick actions flyout immediately right of Manage pins. Show the four shared slots in direction order, an action or assignment choice for each, and Edit assignments. Preserve native keyboard navigation, focus return and lazy provider startup. Remove the rail Down shortcut and guide hint. Keep direct D-pad invocation and the assignment menu on the wheel.
- A valid press briefly compresses the hint face. After 300 ms of pending work, a multicolor stroke travels around the rounded edge. Use the same progress treatment on the desktop launcher and identify working slots in its flyout. Respect reduced motion and contrast. The border must not remeasure the wheel contour. Correlate preparation, worker completion and accepted host capture jobs with their invocation; retire feedback on error, cancellation or replacement. Verify fast actions, slow work, rapid presses, hidden/reopened surfaces and keyboard dismissal. The host passes a completion tracker with the exact capability grant. A capability that returns before its accepted work finishes registers the job’s terminal task. The bridge waits for the handler and any registered host work. Capture Library uses this for saved screenshots and clips. Its replay controls, Media Sessions, Spotify, Discord, YouTube and YouTube Music use handler completion. Widgets and templates without declared actions do not enter this path.
- The radial dropdown offers **Assign quick action…** in its global section. Choose the direction first, then browse all actions grouped by widget, alphabetically by displayed provider and action. Capture Library declares its own actions alongside the other widgets. Show current assignments; unavailable actions may be assigned. Offer move/replace, clear, optional same-provider fallback and Back. Clicking a hint or using keyboard/Enter in the menu gives equivalent access without rebinding keyboard arrows. Settings → Controllers exposes the same four assignments; in-tray editing stays in the tray.
- Feedback follows actual command outcome. A displayed Save never becomes Start on press. Start is a separately opted-in fallback, eligible only while off and when starting is allowed, never during buffering, permission denial or a changed session. No silent substitutions, automatic unrelated actions, or optimistic success toasts.

## Ownership and proposed implementation sequence

1. **Preferences.** Persist up to four widget action bindings with optional fallbacks. The host capture provider existed only in local candidates. If the test profile needs conversion when the new candidate is ready, do it once locally and keep that conversion out of the product. Preserve other assignments and explicitly cleared slots. Test round trips, mixed versions, duplicate/invalid inputs and unrelated preference preservation.
2. **Provider contracts.** Inspect static catalog and dashboard capabilities, separate stable assignable definitions from live availability/labels and target-specific commands. Use identity verified by the bridge, scoped to installed instance/authority. Stopped or unloaded widgets remain assignable. Add an opt-in, bounded background command mechanism only where genuinely needed; retain permission, lifecycle, target, sequence and duplicate-action checks. Revalidate the displayed binding before dispatch and in the provider. Never manufacture Visible/Interactive lifecycle, wake every worker, or dispatch a different command on stale input.
3. **Capture and widget integrations.** Keep native recording and replay status in the host. A capture press can wake Capture Library in the background. Keep the selected widget and present needed permission or source prompts over it. Reuse the actual widget handlers and supported operations below. Validate each action against provider state, including account, device, player, session, busy state and permissions as applicable.
4. **Input and native surfaces.** Route physical presses before D-pad/stick merging, one action per press; fence held/repeated inputs across overlays and editor transitions. Share the editor, catalog and binding service between surfaces. Use existing host menu/list, guide glyphs, accessibility and theme styles. Restore focus and support mouse, keyboard, stick and Back. Use actual wheel and rail as the layout baseline.
5. **Qualification.** Run targeted unit, bridge, provider and native input tests. Capture real WinUI screens and transitions after each refinement, critique readability, clipping, focus visibility and input cost, and record corrections. Cover empty, partially assigned, four assignments, disabled, missing provider, buffering, fallback, rapid press, duplicate delivery, Back, mouse/keyboard and reduced motion. Generate a verified isolated candidate; never send messages, join calls or capture real content for validation.

## Initial consumer matrix

### Background worker lifetime for an explicit press

`wakeOnInvoke` belongs to each manifest action and defaults to false. The chooser reads only the manifest. On an explicit press the bridge checks the installed generation and the selected action before preparing a fresh background snapshot. Dispatch still requires a live offer for that same command and target.

For a worker started solely by that press, retain the exact worker run until its own work finishes or a host service accepts ownership. Screenshot and recording actions should hand off a single authorized capture-and-save operation. The host owns the recorder, destination, cancellation, final commit and result banner after acceptance. Starting replay similarly hands buffering to the existing replay service. A receipt for a temporary worker-owned capture ticket is insufficient because worker retirement cleans it up. Ordinary idle unload must not cancel accepted host work. Permission revocation and package removal still apply to the originating package. Widget-owned ongoing work requires retention through its actual completion. These are operation lifetimes, independent of the manifest wake policy.

Start with a five-second grace period after the last shortcut-only invocation completes or hands off its work. A new press within that period reuses the same worker and cancels the pending unload. Begin a fresh grace period when the last outstanding invocation finishes. Include a repeated-small-task test that verifies one worker start for the burst and an unload after the final grace period. Opening the widget or acquiring a longer-lived consumer supersedes this short residency. A pre-existing worker keeps its ordinary policy. A delayed release must never unload a newer worker run.

For work performed inside the widget, give each admitted invocation a work lease scoped to its worker run. Acknowledge admission promptly so opening or leaving the widget never waits on the job's duration. The SDK reports the terminal outcome of the task the handler returns or explicitly tracks, including failure and cancellation. Widget-owned tray work must survive ordinary foreground/background changes. Untracked fire-and-forget tasks cannot extend residency. Remove the lease on completion or worker teardown. Multiple admitted jobs hold independent leases.

Opening the worker's widget promotes the same instance to the usual visible/interactive lifecycle and cancels a pending short unload. Leaving it starts the normal idle policy. When that idle deadline expires, outstanding work and other active consumers still retain the worker. Recheck eligibility after the last lease ends. Completion while visible only releases the work lease. For a worker never opened by the user, apply the short post-work grace. Once opened, measure the normal idle interval from leaving the widget. Completion does not reset that interval. Test both orderings of foreground entry versus a queued unload and of completion versus leaving, plus a failed job, simultaneous jobs and a stale completion after restart.

Qualification must cover retiring the worker mid-clip and mid-replay, finishing the clip exactly once, saving and stopping the same replay session from a new worker, a save slower than the grace period, repeated presses, concurrent opening or pinning, revocation and a stale release after restart. Measure actual worker starts, exits and repeat-press latency.

## Controller-native file chooser

Use one host-owned WinUI file browser for **Open one**, **Attach several**, **Choose a folder**, and **Save as**. Present it on the overlay or on the pin that requested it. The implementation uses the shared native dialog base and palette, controller guide, text-entry keyboard and multi-select conventions. Its directory navigation, selection and save confirmation live in a dedicated file dialog. A floating presentation keeps small pins usable.

**Layout.** Put the task in the title, such as “Attach files to Discord” or “Copy captures”. Show the current folder as a breadcrumb beneath it. Use a short Places column for Downloads, Documents, Pictures, Videos, Desktop and drives. The main pane is a virtualized, folder-first list with names and a compact size or type column when space permits. Open focused on the contents of the starting folder. On a narrow pin collapse Places into one button and keep the contents full width. A footer shows the selection count and the actual action (“Attach 3 files”, “Copy here”, or “Save”). Only Save as needs a filename editor. Use meaningful file-type icons initially.

**Input.** D-pad or left stick navigates, right stick scrolls. A opens a folder, chooses the single file, or toggles a file in multi-select. Holding L2 while traversing files extends selection using the host convention. B returns to the previous location, restoring the folder row and scroll position; B at the starting location dismisses the chooser. Escape cancels; Backspace or Alt+Up goes to the parent. Mouse supports direct selection, double-click folders, checkboxes and a clickable breadcrumb/commit button. Native keyboard users get arrows, Enter, Space to select, and type-to-find. Keep a short controller path to confirm and show the actual shortcut in the guide. Closing restores focus to the initiating control.

**Required browsing and selection behavior**

- Multi-select mode supports controller A and L2, mouse checkboxes, Ctrl+click to toggle, Shift+click for a range, and keyboard Space or Shift+arrows. Keep checked files when focus changes, a filter hides them, or the user visits another folder. The footer shows the total and opens a review list for removing individual files or clearing the selection. Returning the list requires an explicit Attach/Choose action. Honor the requesting operation's count limit, including the SDK's 16-file limit.
- Provide a visible **Search this folder** field, reachable with the controller or mouse and directly with Ctrl+F. Match names case-insensitively within the current directory, including extensions. Apply the request's file-type filter independently, keep folders navigable, and cancel stale search results on navigation. Clearing the query restores the previous row and scroll position. A no-match state keeps the search and location controls reachable.
- Make the breadcrumb an editable **Location** field on click or Ctrl+L. Accept pasted absolute Windows folder paths and UNC shares. Enter or the controller's Go action navigates and returns focus to the list. Pasting a file path reveals the containing folder and focuses the file if the current mode and type filter allow it. Pasting alone never attaches, installs, opens, or overwrites a file. Invalid, inaccessible, or disconnected locations show a recoverable inline error while preserving the last good directory and selection.
- Every required operation is reachable by controller, keyboard alone, and mouse alone. Use normal Tab/Shift+Tab focus order, native editable text with Ctrl+V, wheel scrolling and visible pointer targets. Preserve a separate draft while editing Location or Search so Back/Escape can leave editing before closing the picker.

Acceptance cases include selecting across filters and folders, two files with the same basename, hitting the count limit, range selection in a filtered view, clearing the search, pasting paths with spaces or Unicode, a disconnected UNC share, and a late directory result arriving after navigation. Verify the three input modes independently against Attach, Copy here and Save as.

Revalidate the widget, pin or browser request and selected paths at commit; only the existing trusted host/backend gets paths.

Test opening, rapid folder traversal, Back/cancel, same-name files in different folders, overwrite refusal, removable media, large directories, controller-to-mouse/keyboard handoff, pin dismissal, and ownership loss mid-picker. No new widget filesystem capability is required for the first consumers.

## Candidate qualification

### Proposed availability explanations

The delivery plan covers widget-authored reasons, terminal outcomes and shared banner behavior. [Capture replay and notification plan](capture-replay-and-notification-plan.md)

The tray currently infers availability from executable offers. An omitted offer
can mean several things for the same widget. A scoped SDK extension could publish
a short user-facing reason alongside a declared action ID when the action is
unavailable. The reason would carry no executable command or permission. The
host could show it in the menu and in the existing banner on an explicit press
after checking the current provider and any configured fallback. A stopped or
removed widget and a changed target already have host-owned explanations.
An asleep widget can only supply information the host already has or obtain
fresh state on a wake-enabled press. A post-dispatch failure would need a
separate reason on the invocation result if the same banner should explain it.
