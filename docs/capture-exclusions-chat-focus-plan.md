## Capture exclusion storage

User approved consolidating exclusions into a transactional metadata store separate from the rebuildable index, defining replacement semantics and adding restore-hidden UI. Baseline RemoveLinkAsync created a .unlinked marker by source/path-derived ID, removed the indexed row and its cached metadata/thumbnail, and preserved originals. Scope this change to exclusion authority; do not migrate unrelated metadata without evidence.

Approved bounded implementation: `library-user-state.sqlite` is canonical exclusion authority, separate from disposable `library.sqlite`. It is attached to the existing per-operation SQLite connection under the same profile lock, so query membership uses indexed SQL rather than a parallel in-memory list or a derived visibility synchronization mechanism. Canonical records store only hidden capture snapshots and their stable original identity; ordinary metadata/favorites remain in the existing sidecars. A durable initialization sentinel distinguishes a new profile from a lost canonical database. Corrupt/missing canonical records fail closed for linked discovery, with an actionable error on Hidden/linked operations; owned capture operations remain available when that exclusion database cannot be opened. No automatic empty-store recovery.

New hides bind the existing source/path-derived capture ID to volume serial + file ID. In-place edits of that physical file remain hidden; a different physical file at the same path is rediscovered without inheriting the old hidden metadata. A rename follows existing path identity and is a new entry. Legacy `.unlinked` IDs migrate transactionally as conservative path-scoped exclusions, remaining hidden until explicit Unhide even if replaced. Entries without legacy snapshots gain display metadata only through normal bounded source discovery; unavailable undiscovered legacy IDs are not fabricated into media rows.

Hidden is an organizational discovery policy, not a new authorization boundary. Default Query/Groups/Find/facets omit hidden entries. `CaptureLibraryQuery.HiddenOnly` (default omitted; protocol126) selects hidden entries through the same bounded indexed pipeline. Item response shapes and known-ID metadata/open/thumbnail/playback authorization remain unchanged. SDK `HideAsync` aliases the compatible RemoveLink operation; `UnhideAsync(CaptureLibraryMutationReference)` uses existing Manage permission and returns a normal item. Both operations advance MetadataRevision. Missing originals can be unhidden while their source remains authorized; disconnected/revoked sources are neither discoverable nor readable.

Ordinary library readers, context queries, templates and SDK examples keep default-visible discovery and existing metadata envelopes; no provider-specific host branch. External file recycling remains a separate explicit permission and operation. No shared presentation/focus change is introduced by exclusions.

## Replay owner continuity across reviewed widget updates

Reported failure: the user's AutoStart preference remained on, but replay did not resume after the approved Capture Library27→30 package update. Implementation: shared `WidgetSettingsTransfer` prepares one bounded host-only replay transfer receipt under consent metadata, using the existing private-state CAS/locking/path protections. Receipt contains the exact source/destination owners and expected replay-settings revision. Only a retained, granted WindowCapture capability permits preparation; destination denial is preserved. The catalog completes the receipt after the new active-version commit and before version retention. No pre-publication settings mutation occurs. A completed verified catalog load retries interrupted completion; unselected/unpublished replacements cannot acquire ownership. Source explicit denial and current destination denial prevent completion. Old source consent records may be retired after transfer because the host receipt proves the prior reviewed grant; the successor still needs its own current grant. Save permission remains independently checked by existing save admission.

Completion changes owner and revision only, preserving Enabled, AutoStart, recording options and application approval exactly. Stop/Forget/uninstall or another settings mutation changes the revision and invalidates late completion. Repeated completion is idempotent. Full uninstall's existing revision advance/approval removal prevents pending receipts from resurrecting recording; raw install/replacement and version rollback do not manufacture a reviewed transfer. A post-selection failure reports that the update is selected and completion is pending, rather than claiming the previous version is still selected.

A live broker reconciles a newer durable owner before revoking its cached former owner. It cancels old commands/saves and aborts the old native session, then requires fresh current-owner authorization and approved-application automatic-start admission after the existing bounded scheduling interval. It never retags a running recorder or file lease. Cancelled saves are withheld from returned host work, and automatic admission waits for their retirement. A CAS conflict during the old-owner revoke write rechecks the separately authorized replacement instead of locally disabling its newer durable intent.
