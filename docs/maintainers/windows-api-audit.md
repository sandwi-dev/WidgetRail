# Windows API audit

Reviewed November 22, 2026, against the working tree based on `c26a6ea8`. The table records the findings at review time. The controller and backdrop repairs are recorded below.

## Repair verification

- Foreground acquisition was tested through the production native export with a separate fixture owning foreground. Windows denied direct activation in both cases. The existing attachment path confirmed focus in 43.6 ms with the peer responsive and 3,213.5 ms when the peer stopped pumping messages for 3.2 seconds. Both attempts detached successfully. The fallback remains in service.
- Pin placement reads destination scale through `GetScaleFactorForMonitor` and uses `GetDpiForWindow` on the pin's actual monitor. Both connected displays reported 125% and 120 DPI for a hidden per-monitor-aware window. Mixed-scale monitor movement remains covered by placement policy tests and needs native verification on mixed-DPI hardware.

- Exclusive control now stops the X360 reader, cancels and drains its pending request, and joins it before releasing the target and client. The callback timeout that could terminate the overlay was removed. The native policy suite passed, including 64 local overlapped-I/O cancellation cycles. Physical disconnect under rumble still requires a hardware test. Device discovery now releases the enumeration list once, checks allocations and closes a rejected bus handle.
- The main overlay, desktop dimmer and pinned windows now share a backdrop that pairs window DC acquisition with release and deletes each DWM region. After six warm-up windows, the WinUI fixture measured 50 GDI objects before and 52 after 24 pin create/close cycles with six DWM reconfigurations per cycle.

## Windows implementation details used as hints

- **Startup status.** Settings interprets a 12-byte Explorer `StartupApproved\Run` record and four byte values. Microsoft documents the separate `Run` registration mechanism. I found no published contract for this approval encoding. The code reads the approval record, writes only its own Run value and reports an unknown format conservatively. The risk is an inaccurate status after a Windows change. [Source](../../src/PlatformSettings/StartupRegistration.cs#L60) · [Run-key documentation](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)
- **Monitor identity.** The display provider splits a monitor interface path on `#` and constructs an `Enum\DISPLAY` registry path to find EDID. Microsoft explicitly says to treat the device-interface symbolic name as opaque. Returning no identity on an unfamiliar layout avoids a crash but can prevent a monitor profile from matching. Resolve the device through SetupAPI before reading its device key. [Source](../../src/WindowsDisplayProvider/MonitorHardwareIdentity.cs#L47) · [Device-path contract](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdigetdeviceinterfacedetailw)
- **Shell window classes.** The running-app and activity filters recognize Explorer implementation names such as `WorkerW` and `Shell_SecondaryTrayWnd`. They supplement visibility, ownership and style checks. Changes can cause an unwanted shell surface to appear among eligible applications. [Running-window filter](../../src/WindowsAppLibraryProvider/WindowsRunningWindowPolicy.cs#L67) · [Activity filter](../../src/WindowsActivityProvider/WindowsActivityNativeAdapter.cs#L96)

## Evidence and limits

This was a source and import-table audit. It covered direct native imports, dynamic loading and ordinals, manual COM interfaces, input and foreground handling, device I/O, registry dependencies, and relevant shipping and diagnostic entry points. The managed import search found 75 C# files in `src`, `samples` and `integrations` outside Validation directories. The audit also inspected the vendored controller client, the pinned WinUIEx backdrop source, and the production native build recipe.

For the running x64 candidate, I inspected the PE import tables for `OverlayPlatformInterop.dll`, `WinUiWindowPreviewNative.dll` and `WebRtcCapturePrototype.dll` and resolved their static ordinal imports against the installed system DLLs. These mapped to public functions such as `D2D1CreateFactory`, `ActivateAudioInterfaceAsync` and OLE Automation functions. The direct NTDLL imports in the platform DLL were runtime unwind, context and code-address helpers. The XInput dependency was found in source because it is resolved at runtime.

The DWM border and corner attributes used by the shell match the installed SDK. The display provider’s hand-indexed DXGI calls and the preview’s compositor swap-chain interop target published interfaces. Their hand-written ABI bindings warrant regression coverage. HidHide and ViGEm IOCTLs belong to their respective drivers. Discord web-client internals are a separate third-party compatibility dependency. [DWM call sites](../../src/OverlayFrontend.WinUI/Shell/OverlayWindowFrame.cs#L129) · [DXGI binding](../../src/WindowsDisplayProvider/DxgiDisplayModes.cs#L20) · [Compositor binding](../../src/OverlayFrontend.WinUI/Previews/WindowPreviewSurface.cs#L277)

The failure conditions above are inferred from source and documented contracts. This review did not induce a controller disconnect, stall another application, change the default audio device, measure GDI growth, or certify all transitive binaries or Windows versions.
