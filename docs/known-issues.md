# Known issues and active bug ledger

This file is the durable source of truth for user-visible bugs found during
local product testing. Roadmap items describe planned capability; entries here
describe behavior that is already expected to work or a current interaction
that must be replaced. A bug is not closed until its acceptance evidence passes
in the packaged Release overlay and the closing commit is recorded.

## Status vocabulary

- **Open** — user-visible behavior is confirmed and acceptance work is not yet complete.
- **Confirmed** — reproduced by a user or deterministic/local evidence.
- **Investigating** — the owning layer is being traced; no root-cause claim yet.
- **Implementing** — a root cause and durable design are selected.
- **Verifying** — the fix is implemented and awaiting packaged/local evidence.
- **Closed** — acceptance evidence and closing commit are recorded.

disposition. Detailed evidence, superseded hypotheses, old acceptance runs, and
per-issue narrative through this compaction are retained in the immutable
[2026-08-11T23-24-15-07-00 snapshot](history/known-issues/2026-08-11T23-24-15-07-00.md)

Use `docs/delivery-plan.md` to select implementation work. A row marked
Verifying remains open for the named packaged, physical, authentication, or live
user check. Promote a row back to Confirmed or Implementing only for fresh
evidence. Close an issue only after the accepted packaged path and closing
commit are recorded in this table.

When new evidence materially changes an issue, update its table row first. Add
a short detail section below only when an open investigation needs evidence that
cannot be expressed safely in the row. Do not restore closed chronological
history to this active file. Snapshot again only after the active ledger exceeds
1,000 physical lines.
