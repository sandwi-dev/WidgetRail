## Decisions

- Extend `WebBrowserDocument` / `UI.WebBrowser`; no Discord-only browser or DOM adapter.
- Browser chrome is a presentation choice independent of profile persistence, background policy, and interaction entry. Webapps use full-page content with LS-accessible controls. Preserve B's framework behaviour.
- Browser state remains host-owned. Profile keys are bounded logical names scoped by widget identity, never paths. Separate persistent and private namespaces. Widget IPC never carries cookies, tokens, browser objects, or arbitrary scripts.
- Keep existing ordinary browsers private by default for compatibility; the explicit webapp configuration opts into persistent sessions. Restricted provider documents stay private and cannot request webapp privileges.
- Website permissions are user decisions scoped to widget/profile/origin and permission kind. A widget declaration is not a permission grant. Clear-data and revoke flows require explicit user action and must affect all live views of the profile coherently.
- Controller text entry must support password fields and standards-based rich editors through browser editing mechanisms. No Discord selectors or direct DOM text replacement. Keep submission explicit and preserve physical keyboard/mouse input.
- Background eligibility is explicit, bounded, and user-visible. Active calls must not silently disappear due to hidden-surface eviction. Stopping a session must terminate its media activity rather than only muting it. Authority revocation, disable/uninstall, and app shutdown still retire sessions.
- Authentication child windows must preserve opener relationships when required, with bounded host-owned lifecycle. Offsite navigation, downloads/uploads, dialogs, and context actions must be accessible and maintain origin visibility.
- CLI scaffolding extends the existing transactional `wrail new` template system; name and HTTPS URL produce a pinnable webapp widget. SDK authors have the same capabilities without the CLI.
- Ship Discord using that authoring path, document honest platform limitations, and verify actual signed-out compatibility before claiming it works.

## Accepted notification experience

- Use WidgetRail-owned presentation only; do not send these notifications to Windows toast UI or Notification Center. This is a shared host webapp feature, not Discord-specific UI or DOM inspection.
- After website notification permission is granted, default presentation is **Banner + list**. Offer **List only** and **Off** per widget, separately from website permission; preferences survive restarts.
- Show at most one compact passive banner for about four seconds (duration configurable in code), without stealing focus, opening the overlay, or taking game/controller input. No sound or vibration by default; honor the website's silent request. Reuse shared layering rules and avoid covering active tray/dialog controls; while those controls are in use, update the notification indicator/list instead of presenting an obstructing banner.
- Banner expiry only hides the preview. It does not dismiss the notification or send a website close event. Keep a pending entry until user activation/dismissal or website withdrawal; notification persistence here means availability after the banner hides, not guaranteed actionable notifications across app restarts.
- Show a subtle pending count in the overlay tray and provide a controller-navigable notification list. No persistent flashing badge over the game and no extra global shortcut.
- In the list: **A** activates the owning widget (or its existing pin) and reports the click to the website; remove the pending entry after activation/callback succeeds. **X** dismisses the selected entry; **B** closes the list without clearing it. Provide an explicit **Clear all** action. Failed/stale activation must not silently lose the item or target a replacement browser session.
- Coalesce rapid notifications from the same widget into a single banner without repeatedly extending its visible lifetime. Retain separate list entries unless matching website replacement tags identify an update; scope those tags to the correct widget/profile/origin. Handle website-requested closure and replacement/renotify semantics without duplicate callback delivery.
- Use bounded storage, queued work and image loading with an explicit overflow policy. Do not silently time-expire ordinary pending entries merely to make the banner disappear. Notification title/body/media must not enter diagnostic logs; lifecycle handling must account for stopped/reloaded/crashed sessions, permission changes and widget removal without retaining dead native notification objects.
- Verify custom display, report-shown timing, click/dismiss/website-close callbacks, tag replacement, bursts, list-only delivery, quiet presentation, main/pin activation and stale session cleanup with synthetic pages. Do not keep a WebView notification deferral open waiting for the user. Actual Discord emission/conversation navigation remains user acceptance; no generic reply/accept-call actions or closed-app push are promised.
