## Decisions

- Extend `WebBrowserDocument` / `UI.WebBrowser`; no Discord-only browser or DOM adapter.
- Browser chrome is a presentation choice independent of profile persistence, background policy, and interaction entry. Webapps use full-page content with LS-accessible controls. Preserve B's framework behaviour.
- Browser state remains host-owned. Profile keys are bounded logical names scoped by widget identity, never paths. Separate persistent and private namespaces. Widget IPC never carries cookies, tokens, browser objects, or arbitrary scripts.
- Keep existing ordinary browsers private by default for compatibility; the explicit webapp configuration opts into persistent sessions. Restricted provider documents stay private and cannot request webapp privileges.
- Website permissions are user decisions scoped to widget/profile/origin and permission kind. A widget declaration is not a permission grant. Clear-data and revoke flows require explicit user action and must affect all live views of the profile coherently.
- Controller text entry must support password fields and standards-based rich editors through browser editing mechanisms. No Discord selectors or direct DOM text replacement. Keep submission explicit and preserve physical keyboard/mouse input.
- Background eligibility is explicit, bounded, and user-visible. Active calls must not silently disappear due to hidden-surface eviction. Stopping a session must terminate its media activity rather than only muting it. Authority revocation, disable/uninstall, and app shutdown still retire sessions.
- Authentication child windows must preserve opener relationships when required, with bounded host-owned lifecycle. Offsite navigation, downloads/uploads, dialogs, and context actions must be accessible and maintain origin visibility.
- CLI scaffolding extends the existing transactional `wrail new` template system; name and HTTPS URL produce a pinnable webapp widget. SDK authors have the same capabilities without the CLI.
- Ship Discord using that authoring path, document honest platform limitations, and verify actual signed-out compatibility before claiming it works.

## Additional usability and content-pinning work (user feedback after candidate 06)

- **Shared pin window ordering:** interpret the requested behavior as a passive pin below the visible main overlay/tray, with the interacting pin raised above it; a passive pin must still remain visible above the game when the overlay is hidden. Screenshot shows the pin occluding the main tray menu. Coordinate this in the shared host presentation/window owner for all pin types, including modal/fullscreen precedence, without moving/recreating the live browser just to change stacking. Current `PinnedWidgetWindow` is always-on-top; `SetInteraction` changes input styles but does not explicitly reconcile relative window order. This is a lead, not a completed diagnosis.
- **Website controls actions:** `HostChoiceDialog` labels its multi-choice primary action `Open`, which executes the selected option (including the separate confirmation for Stop). Replace this ambiguous menu interaction with clear direct actions or a meaningful selected-action label, preserving confirmation for destructive/session-ending operations. Review the shared choice UI rather than adding a Discord-only workaround.
- **Controller editing:** A-click already attempts automatic keyboard entry on supported input/textarea/contenteditable fields. R3 is the manual focused-field fallback. Make that fallback context-sensitive (or remove the redundant mapping after confirming automatic entry covers the supported flows), and stop leaving a permanent "Select an editable text field" status when no field is eligible. Preserve a convenient way to reopen editing after dismissing the keyboard. Add rich-editor/frame coverage where gaps are found.
- **Pin a webapp's pop-out content — design/feasibility:** Discord's reported pop-out matches the generic hosted `NewWindowRequested` path: a child WebView sharing its parent's profile/opener, presented over the original page; B closes it. Prefer a host-owned "Pin this pop-out" action that places that same live child in the existing pin while the parent session remains alive and usable. Do not duplicate the URL/session or extract Discord media/DOM nodes. Assess parent-child lifetime, unpin vs close, parent stop/navigation, replacement of an existing pin, focus/B behavior, and popup capacity through the shared presentation framework. This is not implemented or promised supported for every site. Keep the existing single-pin model unless separately approved.
- **Advanced WebView capabilities assessment:** distinguish native hosted windows, website fullscreen/media/notification APIs and device permissions from features needing injected scripts/site adapters. There is no established generic host API that identifies an arbitrary site's "shared content". Sites with a real pop-out offer the cleanest first route; Picture-in-Picture/runtime-specific behavior needs a focused capability probe before advertising it. No live account probing or stream manipulation is authorized by this planning discussion.

## Progress: background residency, stop and recovery

- The `WebApp` preset now requests `Background.KeepAlive` by default. Authors do not need a matching manifest residency policy: the host acquires a bounded lease for the exact published document and worker incarnation. Ordinary browser defaults remain Automatic. Widget lifecycle remains Background, so retention does not enable hidden widget actions or privileged host services.
- New `browser-retention` Bridge request/response roots have generated JSON metadata. Registry validates current worker, declared KeepAlive document and a four-document global limit. Retention cancels idle unloading; release re-enables it. Stale releases cannot affect replacement workers. Catalog changes, stopped workers and removed declarations invalidate old holds. No release starts a missing worker.
- Native BrowserOwner excludes retained pages from hidden-page eviction. Per-entry session gates serialize acquire/stop/release. Uncertain acquisition attempts are tracked for cleanup; normal requests have a five-second deadline and retirement release has a two-second deadline. Retiring controllers count against the four-surface budget, block replacement at the same key until cleanup finishes, and are drained before a borrowed XamlRoot or owner is disposed.
- Stop is available in website controls and each running/failed webapp's tray menu, with confirmation. It navigates to an empty document to end media/connections, then releases the lease. The stopped page can restart, and address/history/authored navigation must reacquire its session before reviving it. Back/Forward cannot resurrect a stopped document. Explicit stop wins over profile-reset restoration. Host-confirmed stop/reset accepts a page's beforeunload confirmation without introducing a second prompt.
- A shared status label reports running/disconnected webapps, with names in its tooltip; there is no permanent healthy-session footer inside the page. Renderer/browser exits show a recovery message and A-to-reopen guide. Reopen retires the old controller through the existing placement owner. Recoverable GPU/utility failures do not discard the page/call. Failed background pages retain their recovery notice rather than disappearing through LRU eviction; users can stop/reopen them.
